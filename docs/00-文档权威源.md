# 00 · 文档权威源与阅读顺序

> 目的：解决“40 份文档，以哪份为准”的问题。**实现只认这里的层级，不认旧文档里的历史表述。**

---

## 1. 权威层级

| 层级 | 内容 | 地位 | 冲突时 |
|---|---|---|---|
| **L0** | `contracts/spec/*.py`、`schemas/`、`generated/` | **机器真相**：API/事件/类型 | 最高；文档与它不一致时改文档 |
| **L1** | `28–34` | **v1.0 基线**：需求、API、UI 状态、数据模型、模块接口、包划分、ADR | 次高 |
| **L2** | `35–47` | **增量与评审**：缺口清单、对照、缺陷、补齐方案、Spike、路线、DSH 补丁 | 其中标注“修订/定稿/已定稿”的条目**覆盖** L1 对应段 |
| **L3** | `01–27` | **历史与参考**：能力盘点、Octop 分析、早期设计 | **不作为实现依据** |
| **L4** | `prototype/` | 交互参考，不参与生产 | 仅用于体验验证 |

**判定规则**

1. 先看 `contracts/spec`；没有契约的，看 `28–34`。
2. `35–40` 中带“修订 / 定稿 / 已定稿 / 已补齐”的段落优先于 `28–34` 同主题。
3. `01–27` 只用于“为什么这么设计”，不用于“现在怎么做”。
4. 任何新需求必须同时更新 `28` 与至少一个下游（`29/30/31/11`），否则 `coverage_check` 报 `HARD`。

## 4. 阅读顺序

- **产品/设计**：`39` → `40` → `28` → `30` → `04`
- **后端**：`32` → `31` → `29` → `02` → `13`
- **前端**：`30` → `04` → `33` → `generated/ts`
- **测试**：`28` → `19` → `20` → `coverage_check`
- **新人**：`README` → `00` → `28` → `02` → `32`

---

## 5. 变更规则

1. 改 API/事件：先改 `contracts/spec` → `generate` → `check` → 再改文档。
2. 加需求：`28` 新 ID + 端点/表/测试 ID；`coverage_check` 必须过。
3. 改表：`31` 表清单 + DDL + 枚举 + 迁移；同步 `02 §4.2` 计数。
4. 改交互：`30` 状态表 + `04` 页面规格；新域必须有可点击原型。
5. 任何“修订/定稿”写到 `35–40` 时，必须在对应 L1 文档留一行指针，避免只活在补丁里。

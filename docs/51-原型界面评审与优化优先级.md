# 51 · 原型界面评审与优化优先级

> 评审对象：`prototype/`（L4 交互参考，非生产代码）
> 评审日期：2026-11-26
> 评审方式：只读。逐张看 `prototype/shots/*.png`（52 张）、通读 `app.js`（3978 行）/`styles.css`（650 行）/9 个独立 `*.html`，并做 `data-act` ↔ `switch(act)` 全量比对。
> 本文性质：评审记录，**不修改** `04/30` 规格。若采纳，按 `00 §5` 回写 `30` 状态表 + `04` 页面规格。
> 不视为缺口的：无后端、数据写死、流式用定时器（README 已声明边界）。
> **算缺口的**：交互承诺了但内存 state 不更新（"假成功"）——同类操作在用户/提供商/存储上已真实落 state，说明原型本身具备该能力，不是能力边界问题。

## 1. 总评

**一句话**：原型的"页面覆盖广、单页视觉完成度高"，但"跨页流程闭环薄"——大量动作停留在 toast 与 DOM 层，进入第二轮评审（照着点一遍）就会在 4 条主线上断掉：**发起→审批→执行→归档**、**上传→索引→检索→重建→删除**、**编辑→发布→回滚**、**添加→授权→过期→恢复→删除**。

按"能不能演完一条流程"分四档：

| 档位 | 模块 | 说明 |
|---|---|---|
| ✅ 可用闭环 | 用户管理（增/删/改状态/邀请）、插件（装/卸/启停）、技能包（装/更新/启停）、快捷键/主题/配色/密度、环境变量（校验+回滚）、KV 级会话操作（改名）、终端/浏览器占位说明 | 这些是原型里"点得动、看得见结果"的部分 |
| ◐ 半闭环 | 对话（发消息/停止/队列/编辑重发/Ask/Plan/审批三选）、任务（建单/选桶/停止/追加预算）、工单详情（只读）、专家抽屉（字段可编辑但不保存）、知识库文档（删除/预览/选择）、连接器抽屉（可开可配） | 有交互，但关键动作不落库或缺终态 |
| ○ 假操作 | 自动化、通道、ACP、云端协同（部分）、用量时间范围、模型配置 6 个 Tab、安全防护开关、知识库设置、语言/布局、通知开关以外的设置 | 表是局部常量或只改 chip 高亮 |
| ✗ 死路 | 新建知识库、专家配置文件编辑/导入导出、工单详情审批、收件箱批量决策、"全部已读"、9 类表单、移动端详情 | 点击无反应 / 无按钮可走 / 状态卡死 |

**最该先修的不是视觉，是"假成功"**：它比"按钮没反应"更危险——评审会以为能力已具备，实现阶段才发现交互契约是空的。

## 2. P0（阻断闭环，评审前必须处理；10 项）

### P0-1 对话里没有任务卡，核心叙事断链

- 现象：`renderMsg`（app.js:766-824）只渲染"审批卡"，没有懒 Ticket 任务卡。带副作用的请求（写文件/跑命令）在对话中不会出现"建议创建任务/创建中/待审批/预算告警/失败/完成/取消"。
- 唯一的任务卡实现被放在孤岛文件 `task-card.html`，且它的 8 个状态（建议/创建中/运行/待审批/预算/失败/完成/取消）与主壳任务中心的 4 个桶（待决/进行中/排队/已完成）**是两套状态机**——主壳根本没有"失败"和"已取消"。
- 影响：产品最核心的能力（人授权 Agent 干活、可审计可停止）在原型里无法演示；`04 §6.7` 的事件驱动链只能靠旁白。
- 建议：把 `task-card.html` 的状态机搬进 `renderMsg`，作为 assistant 消息的一种卡片；主壳任务桶补齐 失败/已取消，并让任务卡"查看任务"跳到工单详情。

### P0-2 9 类表单"保存成功"但零落库

- 证据：`form-save`（app.js:3104-3181）只处理 7 种 kind：`user / profile / subagent / bridge / provider / storage / session-rename`。以下 9 种进入同一弹窗但**没有分支**，最后统一走到 `state.modal=null; render(); toast("已保存")`：
  `group / channel / acp / acp-config / connector / mcp / cron / kb-file / kb-folder`
- 后果（按页面）：
  - `/automation`：创建定时任务永远不新增；"编辑"复用创建弹窗；删除只 toast；表格是 `renderAutomation` 内 `const allJobs`（1169），每次渲染重建。
  - `/channels`：新建通道不新增；表格是局部常量（1306-1314）。
  - `/acp`：添加 Runner 不新增；表格是局部常量（1389-1396）。
  - `/connections` 自定义 MCP：添加/编辑 Server 不新增、保存 JSON 丢弃 textarea。
  - `/knowledge`：新建文件/新建文件夹不新增任何文档。
  - 用户管理"编辑分组"同样假成功。
- 影响：这些页面在评审时"能打开、能填写、提示成功"，但数据不变——比禁用更糟。
- 建议：要么落 state（照 `storage`/`provider` 的写法，成本很低），要么把按钮改成 disabled + "v1.1 未接入"；不允许"提示成功但什么都不做"。

### P0-3 "全部已读"把待决任务打死

- 证据：`inbox-read-all`（3680）遍历所有 attention 置 `resolved=true`，但**不改 `task.bucket`**；而任务卡只在 `bucket==="attention" && !resolved` 时渲染决策按钮（1057）。结果：任务仍留在"待我决定"桶，卡片上**没有任何按钮**，详情页也不显示审批操作，只能靠"停止/重新派工"绕出去。
- 语义问题：`全部已读` 是通知语义，却对审批生效，等于"静默批准/丢弃"。与 `04 §5.15` 的"默认不静默自动批准"直接冲突；文档也没有为"Attention 是否可批量已读"给结论（`30 §14A.8` 明确 Attention 需要决策、Notification 只告知）。
- 建议：拆分两个动作——"标记已读"（只改未读态，不移出待决）+ "批量决策"（需 L4 确认：范围+动作+时长）；或直接删掉"全部已读"，只保留逐项决策。

### P0-4 收件箱回答会空提交

- 证据：`att-filter`（3668）把 `selectedAttention` 置 `null`；`answer-submit`（3670）只开弹窗、不记录 id；`answer-save`（3671）用 `state.selectedAttention` 去解析 → `resolveAttention(null)` 直接 return（2757-2760）。于是：先切一次筛选，再点某条"提问 → 提交回答"，弹窗提示"已提交回答，Agent 继续"，但该 attention 仍在收件箱。
- 附带：回答弹窗不校验空值，空回答会写入"（空）"。
- 建议：`answer-open/submit` 用 `data-id` 显式传 id（照 `answer-open` 的做法），不要依赖全局选中态。

### P0-5 知识入库没有终态

- 证据：`upload-save`（3740）固定新增 `new-doc.pdf`，不读文件输入框；置为 `processing` 后**没有任何代码把它变 ready**（唯一通路是批量重建 3707 直接置 ready）；上传进度条固定 62%（1695）；`doc-reindex`（3753）置 `processing` 后永久"解析中"；`KBS[].docs/chunks`（199-202）与侧栏/页副标题（645、1657）从不更新。
- 影响：用户无法判断文档是否可被检索；"失败"的 `legacy-notes.docx` 无原因、无重试强调；删除后 KB 计数不变。
- 建议：加一次 `setTimeout` 把 `processing → ready`（或 → failed）并同步计数；上传读 `input.files[0].name`；失败行内给原因+重试主按钮。

### P0-6 专家保存/发布/回滚全不落库

- 证据：`agent-save`（3793）/`agent-publish`（3794）只 `state.drawer=null; toast(...)`，抽屉里 9 个分区的字段（名称/描述/欢迎语/模型/温度/心跳/人格…）**从不读取**；`agent-publish` 提示"已发布 v4"，但版本 Tab（1879）恒为 v3/v2/v1；`agent-rollback`（3810）仅 toast；头像/配色/子智能体开关均为 DOM 级。
- 附带：抽屉没有脏检查（`close-drawer` 3792 直接销毁，只有 `closeModal` 有 guard），而页头常显"有未保存修改"（1803）——这个徽章本身就是假状态。
- 建议：至少让"名称/描述/模型"回写 `AGENTS[]`，发布时 `versions.unshift(v4)`；抽屉关闭接 `closeModal` 的 dirty 逻辑；徽章改为真实 dirty 态。

### P0-7 连接器生命周期不生效

- 证据：`renderConnections` 的 `enabled` 是函数内数组（1905-1909）；`conn-save`（3043）只校验显示名、不回写；`conn-delete`（3073）只关抽屉 + toast；`conn-default`（3063）只 toast；`conn-add`/MCP 添加走无分支表单（见 P0-2）。
- 关键路径断点："已过期 → 重新授权 → 已连接"：`oauth-complete`（3060）只改 `state.connector.status`（抽屉里的临时对象），重渲染后列表重新生成 → 仍显示"已过期"；卡片上也没有"重新授权"主操作（只有配置/测试/删除）。
- 建议：把连接器列表提为 `state.connectors`；过期卡主操作改为"重新授权"；删除需 409 引用阻止提示。

### P0-8 工单详情不可达，且待决项在详情里无审批

- 证据：`renderTicket`（1145）存在，但**全站没有任何跳转**（只有手输 `#/ticket`）；点任务卡走的是 `tasks/:id` → 仍是 `renderTasks` 分栏，不是工单页。
- 更严重：`renderTaskDetail`（1117-1143）对**任何桶**都渲染"重新派工/追加预算/停止"（1130-1132），待决任务在详情里**没有批准/拒绝**；已完成任务仍可"停止"。
- 影响：`ticket.png` 截图就是"待我决定"却在详情页无法闭环；已结束任务可再次停止，状态机被破坏。
- 建议：详情页按桶分支动作（attention→批准/拒绝/回答/追加；running→停止/追加；done→查看报告/重跑/归档）；补"返回列表"与"打开完整工单"；把 `renderTicket` 接成详情入口，删掉重复实现。

### P0-9 权限门禁漏洞：只读角色能批准、能停任务

- 证据：`ACTION_PERM`（244-253）只登记 18-24 个动作；`approve / approve-session / deny / task-stop / task-assign / task-budget / answer-save / user-delete / plugin-remove / cron-delete` 等**均未登记**，`applyPermissions`（2540）因此不禁用它们；而 `/tasks` 对 auditor 是可见的（`ROLE_PERMS.auditor` 含 `tasks`）。
- 另有：非 button 的 `[data-act]` 只加 `aria-disabled` + class，点击仍然触发（2780 不检查 disabled）。
- 影响：安全演示自相矛盾——只读审计能批准 shell.exec、能停任务。
- 建议：补齐写操作权限映射（`tasks:write` / `attention:write`）；点击委托入口统一判 `el.disabled || aria-disabled`。

### P0-10 深色模式消息气泡不可读（视觉）

- 证据：`dark.png` 用户消息气泡近白底 + 更浅的浅蓝字，正文对比度极低（截图像素估算 ≈1.2:1）；会话选中行同样被浅色覆盖压暗。
- 原因：`.msg.user .msg-text` 用 `var(--primary-soft)` + `var(--primary-border)`，深色主题下 `--primary-soft` 是深蓝（#12233d）但文字仍是 `--text`… 实际截图显示为浅底浅字，说明深色下气泡背景未跟随（或截图取自旧版 CSS）。
- 建议：深色下气泡改 `background: color-mix(...)` 或固定深蓝底 + 高对比文字，并纳入对比度校验（AA 4.5:1）。这条无论代码还是截图都必须先复现确认。

## 4. P2（一致性与体验打磨；10 项）

1. **用量页时间范围无效**：`usage-range`（3824）不参与渲染，7/30/90 天数据相同；图注写"近 14 天"与筛选"近 30 天"矛盾；柱图每根都有 100% 高的浅色底柱（`.bars i` 背景 + `::after`），视觉上像"每根都超 100%"；"按专家"两列数值无列头（774K / ¥115.6 分不清）；"人工干预率 0.42"无单位。

## 5. 布局与按钮"和谐度"专项

### 5.1 层级与密度

- 3 列固定外壳（220 rail + 268-280 side + 内容）在 1600 宽下只剩 ~1050 内容区；任务页再切 440 列表 → 详情仅 ~610，`授权范围` 的 `scope` 三个 code chip 被挤到换行。
- 同一屏最多出现 3 份同一目的地入口（管理/连接器/技能包）。
- 专家页 4 个实体同时出现在侧栏列表、卡片网格、"新建专家"虚线卡（第 6 格）；网格 3 列后排 4+空 2 格。

### 5.2 按钮形态（建议固化为 4 级）

| 级别 | 用途 | 现状违规 |
|---|---|---|
| 主（实心，≤1/屏） | 创建/保存/批准 | 市场整列主按钮；连接器空态两个主按钮；专家页"新建专家"3 处 |
| 次（描边） | 常规操作 | 与文字链混用于同一操作列（技能"更新"文字链 + "停用"描边） |
| 文字（低权重） | 详情/测试/取消 | 用户行 3 个文字链；自动化每行 3 个文字链 ×3 行 = 9 个 |
| 危险（红，永远最右 + 确认） | 删除/停止/拒绝 | 与主操作相邻（连接器抽屉"测试/删除/取消/保存"四个一排）；"解绑"用中性描边 |

另外：确认分级缺失——全站没有 L4（输入资源名/数量），删用户、恢复备份都只要一次确认；`15 §1.2` 的 L3/L4 在 `30 §13` 被抹平成"二次确认"，原型照 `30` 实现，于是 L4 消失。

### 5.3 表格与卡片

- 表格三种行高、列宽失控（技能表"来源/版本"间 200px 空档；知识库文档表文件名列 ~400px、状态列 40px）。
- 只有 3-4 行数据也显示"第 1/1 页 + 6/页 + 上一页/下一页（禁用）"——分页控件看起来像坏了。
- 状态表达双轨：`状态徽标 + 开关` 同时表达同一件事（插件表、通道表）；`必开` 用灰字；三色状态点无图例（专家卡）。

### 5.4 深色与响应式

- 深色气泡不可读（P0-10）；深色下选中行也被浅色覆盖。
- ≤1360 隐藏右侧悬浮操作条、≤1120 隐藏 Dock、≤960 隐藏详情栏——功能随视口"消失"而非"降级"，且按钮文案仍显示"打开/收起 Dock"。
- 移动端 5 个 Tab 在 500px 内顶满、无滚动提示；"新建任务"与"筛选"被拆成两行（一个左下、一个右上）。

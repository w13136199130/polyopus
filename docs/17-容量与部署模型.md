# 17 · 容量与部署模型

> 回答三个问题：**一台机器能扛多少？什么时候拆？拆完怎么部署？**
> 数字是**可验证的估算**，不是承诺；每个阈值都给出压测方法与触发告警。上线前用真实负载校准一次。

---

## 1. 工作负载画像

### 1.1 单位定义

| 单位 | 定义 | 用途 |
|---|---|---|
| **ACT** | 活跃并发轮次（Active Concurrent Turns） | 容量的第一指标 |
| **TPM** | 每分钟新 turn 数 | 入口压力 |
| **Tickets/day** | 每日工单数 | 工作系统吞吐 |
| **Chunks** | 向量切片总数 | 检索与存储 |
| **Events/day** | 每日事件数 | 写入与归档 |

**Little 定律**：`ACT ≈ TPM × 平均 turn 时长（分钟）`。
例：30 TPM × 2 min = 60 ACT；峰值按 2–3 倍均值预留。

### 1.2 单 turn 的资源画像（估算）

| 项 | 典型值 | 说明 |
|---|---:|---|
| 模型调用 | 2–4 次 | 含工具间推理 |
| 工具调用 | 2–6 次 | 读文件/检索/HTTP |
| 事件数 | 80–150 条 | token 批量后 |
| 输入 token | 8k–40k | 含记忆/知识 |
| 输出 token | 0.5k–3k | |
| DB 写 | ~150 行 | 事件+消息+用量+租约 |
| 对象存储 | 0–2 MB | 附件/产物 |

### 1.3 单日增长（1 万 turn/天）

| 数据 | 日增 | 90 天 |
|---|---:|---:|
| 事件 | ~36 MB | ~3.2 GB |
| 消息 | ~50 MB | ~4.5 GB |
| 用量/审计 | ~5 MB | ~0.5 GB |
| 附件/产物 | 2–20 GB | 180 GB–1.8 TB |

> 附件是存储主导项；必须走对象存储 + 生命周期，不进 PG。

### 1.4 向量规模

| Chunks | 原始向量（1024 维 float32） | HNSW 索引估算 | 检索 p95（HNSW） |
|---:|---:|---:|---:|
| 100k | 0.4 GB | ~0.7 GB | < 20 ms |
| 1M | 4 GB | ~7 GB | 30–60 ms |
| 10M | 40 GB | ~70 GB | 80–200 ms（需调参/分片） |

> 超过 2M chunks 就要认真评估：HNSW 内存、重建时间、是否拆独立向量库。

**多实例机制（2026-11 定稿，v1.1 启用；v1.0 建表不启用）**

1. **实例注册**：进程启动写 `instances(instance_id, role, version, started_at)`，每 15s 更新 `last_heartbeat`；心跳超 60s 视为离线，调度忽略该实例。
2. **配置共享**：配置/权限/插件/策略包变更写 `config_versions(scope, key, version)`，一次递增；实例轮询（≤5s）或经 Redis 订阅失效通知。
3. **缓存失效**：本地缓存带版本号；发现版本变化即清缓存重载；权限/策略/ACL 三类缓存必须走此机制。
4. **cron 单飞**：scheduler 用 DB 租约（`lease_token` + leader 选举）保证同一时刻只有一个调度者；错过补跑只补最近一次（ADR-004）。
5. **WS 扇出**：事件经 Redis pub/sub 广播，各 api 实例只推给自己持有的连接；断线重连从 `after_seq` 回放，不依赖实例存活。
6. **文件真相**：工作区/artifacts 只在对象存储；本地盘只作缓存，实例漂移不丢数据。

> T1→T2 只改配置不改代码；单实例部署时心跳/版本表退化为空转。

### T3 多集群（可选）

按租户分片（tenant → cluster），或按地域。**v2 之前不做**；先把 T2 跑稳。

## 3. 拆分触发条件（什么时候加机器/拆服务）

| 信号 | 阈值 | 动作 |
|---|---|---|
| API CPU p95 | > 65% 持续 10min | 加 api 副本 |
| 队列排队 p95 | > 10s | 加 worker |
| worker CPU | > 70% | 加 worker 或降低并发 |
| DB 连接使用率 | > 70% | PgBouncer / 调池 |
| PG 写 IOPS | > 70% 峰值 | 分区/归档/升配 |
| WS 连接/实例 | > 5k | 启用 Redis 扇出 + 多 api |
| 事件表行数 | > 2000 万 | 月分区 + 归档 |
| Chunks | > 2M | HNSW 调参；> 10M 拆向量库 |
| 租户数 | > 500 | 行级隔离强化 + 分区 |
| 对象存储 | > 1TB | 生命周期（30 天转冷） |
| 单实例内存 | > 75% | 排查缓存/会话泄漏 |

**扩容顺序**：worker → api → DB 只读 → 分区/归档 → 向量库 → 分片。
**不要先升 DB**：先确认是 CPU/连接/IO 哪一类。

## 4. PostgreSQL 分区与索引

### 4.1 分区策略

| 表 | 分区方式 | 触发阈值 | 保留 |
|---|---|---|---|
| `events` | RANGE(ts) 按月 | > 2000 万行 | 90 天热 + 归档 |
| `usage_records` | RANGE(ts) 按月 | > 1000 万 | 24 个月 |
| `audit_log` | RANGE(ts) 按月 | > 1000 万 | 12 个月 |
| `triggers` | RANGE(received_at) 按月 | > 1000 万 | 30 天 |
| `messages` | HASH(thread_id) 16 片 | > 5000 万 | 永久 |
| `memory_atoms` | HASH(tenant_id) 8 片 | > 1000 万 | 永久 |
| `tickets` | 暂不分区 | > 500 万再 HASH(tenant_id) | 永久 |

```sql
-- events 按月分区（PG 16）
CREATE TABLE events (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY,
  tenant_id TEXT NOT NULL,
  stream_id TEXT NOT NULL,
  seq BIGINT NOT NULL,
  type TEXT NOT NULL,
  payload JSONB NOT NULL,
  ts TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (id, ts)
) PARTITION BY RANGE (ts);

CREATE TABLE events_2026_11 PARTITION OF events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
```

- 分区表主键必须含分区键；业务唯一约束 `(stream_id, seq)` 用**唯一索引**（PG 允许在分区表上建，但需含分区键；替代方案：每个分区内唯一 + 应用层保证）。
- SQLite 不分区：用 `events_archive` 表 + 定期搬迁。

### 4.2 必备索引

```sql
CREATE UNIQUE INDEX ux_events_stream_seq ON events(stream_id, seq);
CREATE INDEX ix_events_tenant_ts ON events(tenant_id, ts DESC);
CREATE INDEX ix_messages_thread_seq ON messages(thread_id, seq);
CREATE INDEX ix_tickets_tenant_bucket ON tickets(tenant_id, state, updated_at DESC);
CREATE INDEX ix_triggers_source_time ON triggers(source_id, received_at DESC);
CREATE INDEX ix_memory_ns ON memory_atoms(tenant_id, agent_id, status);
CREATE INDEX ix_assignments_claim ON assignments(state, lease_until);
CREATE INDEX ix_attention_user ON attentions(assignee_user_id, status, expires_at);
-- 向量（pgvector）
CREATE INDEX ix_kb_chunks_hnsw ON kb_chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

### 4.3 连接池

| 进程 | 池大小 | 说明 |
|---|---:|---|
| api | 10–20 | 每副本 |
| worker | 5–10 | 每进程 |
| scheduler | 5 | |
| **总连接** | ≤ PG max_connections × 0.7 | 超过用 PgBouncer（transaction 模式） |

> 注意：`SKIP LOCKED` 与事务级 advisory lock 在 PgBouncer transaction 模式下可用；session 级 advisory lock 不可用。

## 5. 容量公式

```
ACT        = TPM × avg_turn_minutes × peak_factor
workers    = ceil(ACT × 1.3 / per_worker_ACT)      # 1.3 为余量
per_worker_ACT ≈ 3–5（受模型等待影响，IO 密集）
db_conns   = api_replicas × 15 + workers × 8 + 10
events/day = turns/day × 120
storage/day≈ events + messages + artifacts
```

示例：100 TPM × 2 min × 2 = 400 ACT（超 T2，需分片或限制并发）。
实际先压测得到 `per_worker_ACT`，再反推。

## 6. 压测方案

### 6.1 场景

| 场景 | 负载 | 关注 |
|---|---|---|
| 稳态 | 50 ACT 持续 30min | p95、错误率、DB CPU |
| 阶梯 | 10→100 ACT，每 5min 加 10 | 拐点（knee） |
| 尖峰 | 30s 内 100 新 turn | 队列积压、429 比例 |
| 长会话 | 单 thread 500 轮 | 事件回放、内存 |
| 大附件 | 100MB 并发 5 | 对象存储、内存 |
| 检索 | 1M chunks 下 20 QPS | 向量 p95 |
| 工单风暴 | 100 webhook/s 持续 5min | 去重、队列、Gate |

### 6.2 判定

- 错误率 < 0.5%（不含 429）；
- TTFT p95 ≤ 1.5s（本地模型/假模型）；
- 事件写入 p95 ≤ 100ms；
- DB CPU < 70%，连接 < 70%；
- 队列排队 p95 < 10s。

### 6.3 工具

k6（HTTP/WS）+ 假模型（固定延迟）+ 可选真模型小流量。压测环境必须与生产同规格 DB。

## 7. 扩容 Playbook

1. **确认瓶颈**：看板（CPU/队列/DB/向量/WS）→ 定位到某一层。
2. **先加 worker**（多数情况是等待模型/工具）。
3. **加 api** 时确认 WS 扇出是否已启用 Redis；否则新副本收不到别的实例的事件。
4. **DB**：先加只读副本（读多）；写瓶颈 → 分区/归档 → 升配 → 分片。
5. **向量**：先调 HNSW（m/ef）→ 分 KB 分片 → 独立向量库。
6. **归档**：事件/审计/用量按月归档到对象存储（Parquet/JSONL），DB 只留热数据。
7. **回滚**：任何扩容都可回退；分区/归档不可逆，必须先备份。

## 9. 成本估算（量级）

| 档位 | 配置 | 月成本（云，估算） |
|---|---|---|
| T0 | 1×4c8g | ¥300–600 |
| T1 | 1×8c16g + PG 4c16g + 200GB | ¥1.5k–3k |

| 模型 | 按 token | 通常是最大项（可占 60–80%） |

> 结论：**模型成本 >> 基础设施成本**。容量设计要和"路由/压缩/缓存"一起看，否则加机器不如降 token。

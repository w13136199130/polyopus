## 1. 卡片约定

- **估时**：0.5d / 1d；**超过 1d 必须拆卡**。
- **一张卡 = 一个 PR**；PR 标题带卡号，如 `[M0-07] migrator 核心`。
- **验收必须是命令**，不是描述；命令写进卡片，CI 里同名目标必须存在。
- **依赖**未完成不得开工；并行卡在依赖图上不交叉写同一文件。
- 新卡必须带 `M0-xx` 编号并更新 §2 依赖图，否则不进迭代。

状态图例：`TODO` / `DOING` / `DONE` / `BLOCKED`。

## 4. 任务卡

### A 线 · 仓库与工具链

#### M0-01 · 仓库初始化（0.5d）
- 产出：`.git`、`.gitattributes`（`* text=auto eol=lf`）、`.gitignore`、`LICENSE` 占位
- 做法：`git init`；首次提交只含现有 docs/contracts/spikes/prototype；建立 `main` 保护（本地约定）
- 验收：`git status` 干净；`git log --oneline` 有首个提交；CRLF 不入库
- 风险：直接把 `generated/` 当源码改 → `.gitignore` 不排除（它是交付物），但 CI 校验同步

#### M0-02 · 依赖与工具链（0.5d）
- 产出：`pyproject.toml`、`uv.lock`、`ruff.toml`、`mypy.ini`、`.importlinter`
- 依赖：`fastapi`、`uvicorn[standard]`、`pydantic`、`pydantic-settings`、`httpx`；dev：`pytest`、`pytest-asyncio`、`ruff`、`mypy`、`import-linter`
- 验收：`uv sync && uv run ruff check . && uv run mypy src` 通过（空包也过）
- 风险：Python 3.13 兼容 → 固定 `requires-python = ">=3.12,<3.13"`

#### M0-03 · 包骨架与 CLI（0.5d）
- 产出：`src/polyopus/{__init__.py,__main__.py,cli/main.py}`；`poly --version`、`poly --help`
- 范围：只建 `kernel/ platform/ domains/` 三个空包 + `platform/db`、`platform/events`；**不建 16 个 domain**
- 验收：`uv run poly --help` 列出 `doctor`、`migrate` 两个子命令（先占位）
- 风险：过早铺目录 → 本卡只允许创建 6 个目录

#### M0-04 · Makefile 与本地 CI（0.5d）
- 产出：`Makefile`：`setup / lint / type / test / contracts / doctor / migrate / check`
- 做法：`make check` = lint + type + test + contracts check + coverage_check
- 验收：`make check` 在干净环境一次通过
- 风险：Windows 无 make → 同时提供 `scripts/check.py`，两者等价

#### M0-05 · 配置与 `poly doctor`（1d）
- 产出：`src/polyopus/config.py`（pydantic-settings，TOML + env）、`cli/doctor.py`
- 自检 5 项：Python 版本、数据目录可写、SQLite 版本与 FTS5、迁移状态、时区/时钟
- 验收：`uv run poly doctor` 输出 5 行 `OK`；改坏 `POLY_DB_PATH` 后给可读修复建议
- 风险：doctor 变成杂物间 → 只允许这 5 项，新增需改本卡

### B 线 · 迁移器

#### M0-06 · DDL 抽取器（1d）
- 产出：`tools/extract_ddl.py`、`migrations/_manifest.json`
- 做法：从 `docs/31` 的 ```sql 块抽取 `CREATE TABLE/INDEX`，按表名归并；输出表清单供断言
- 验收：`uv run python tools/extract_ddl.py --check` 报告 `102 候选 / 94 首版`；缺表即失败
- 风险：正则漏表 → 以 `31 §2` 表清单做集合比对，不用计数糊弄

#### M0-07 · migrator 核心（1d）
- 产出：`src/polyopus/platform/db/migrator.py`
- 做法：`schema_migrations(version, name, sha256, applied_at)`；按 version 升序；每个迁移一个事务；已应用则校验 sha256，不符即 `MIGRATION_CHECKSUM_MISMATCH`
- 验收：`uv run pytest tests/integration/test_migrator.py -q` 通过（顺序/跳过/校验和三例）
- 风险：并发启动双跑 → 用文件锁或 `BEGIN IMMEDIATE`，M0 先单进程

#### M0-08 · `0001_core.sql`（12 表，1d）
- 表：`tenants/users/threads/messages/events/turns/runs/steps/tickets/attentions/usage_ledger/schema_migrations`
- 要求：全部带 `tenant_id`（`schema_migrations` 除外）；关键唯一键 `events(thread_id,seq)`；索引齐全
- 验收：空库 `poly migrate` 后 `sqlite3 .schema` 含 12 表；`PRAGMA foreign_key_check` 为空
- 风险：从 31 抄错列 → 用抽取器生成，不手抄

#### M0-09 · 种子数据（0.5d）
- 内容：`0002_seed.sql` 插默认租户（幂等）；`platform/db/seed.py` 建首个 admin（scrypt 哈希，首次迁移生成一次性口令，可用 `POLY_ADMIN_PASSWORD` 覆盖）
- 范围：**policy bundle 延后到 M1**——`policy_bundles` 不在 M0 的 12 张核心表内
- 验收：两次迁移后 `tenants=1`、`users where is_owner=1` = 1；`verify_password` 通过；重复迁移不新增
- 风险：种子写死密码 → 已由运行时生成 + 只打印一次解决

#### M0-10 · `poly migrate` CLI（0.5d）
- 子命令：`poly migrate`（执行）、`--sql`（只打印）、`--check`（只校验待应用）
- 验收：`poly migrate --check` 在空库退出码 1 并列出待应用；`--sql` 不写库
- 风险：`--sql` 与真实执行漂移 → 两者共用同一渲染函数

#### M0-11 · 迁移矩阵测试（1d）
- 用例：① 空库全量 ② 已迁移再跑（幂等）③ 旧库（少一张表）补齐 ④ 中途失败回滚
- 验收：`make test-migrate` 4/4；每个用例独立临时目录
- 风险：测试互相污染 → 每例 `tmp_path` + 独立 DB 文件

#### M0-12 · 迁移错误与诊断（0.5d）
- 内容：错误码 `MIGRATION_FAILED / CHECKSUM_MISMATCH / SCHEMA_TOO_NEW`；doctor 显示"待应用 N 个"
- 验收：篡改已应用文件后启动 → 明确报 `MIGRATION_CHECKSUM_MISMATCH` 并给恢复命令
- 风险：错误信息泄露路径 → 只显示相对路径

### C 线 · 事件存储与恢复

#### M0-13 · events 表与 append（1d）
- 产出：`platform/events/store.py`：`append(thread_id, type, payload) -> seq`
- 做法：同事务内 `SELECT max(seq)+1`（SQLite 单写者）；`(thread_id, seq)` 唯一约束兜底
- 验收：并发 100 次 append 无重复 seq；重复 `event_id` 幂等
- 风险：seq 空洞 → 事务失败即整体回滚，不留洞

#### M0-14 · replay / after_seq（0.5d）
- 产出：`read(thread_id, after_seq=0, to_seq=None)`；`rebuild(thread_id)`
- 验收：与 S1 spike 同数据集重放结果 hash 一致；`after_seq` 不重复返回
- 风险：大线程内存 → 生成器分批，单批 ≤500

#### M0-15 · messages 投影（0.5d）
- 产出：`projection.py`：`message.created/updated` → `messages` upsert
- 验收：重放 1000 事件后 `messages` 与事件推导一致；重复重放结果不变
- 风险：投影与事件双写不一致 → 只允许投影由事件驱动，服务层不直接写 messages

#### M0-16 · 假 turn runner（1d）
- 产出：`workers/turn_worker.py --fake`：写 `turn.started` → 3 个 `step` → `turn.completed`
- 要求：可被 `kill -9` 打断；每步落到 events；不调模型
- 验收：`uv run python -m polyopus.workers.turn_worker --fake --thread t1` 产生 5 条事件
- 风险：假 runner 与真内核分叉 → 接口按 `32 §6` 的 ExecutorEvent 形状写

#### M0-17 · 最小租约（1d）
- 产出：`platform/queue/lease.py`：`claim/heartbeat/release`，字段 `lease_owner/lease_until/attempt`
- 验收：两个进程抢同一 turn，只有一个 running；心跳停止 60s 后可被重领
- 风险：时钟漂移 → 统一用 DB 时间（`CURRENT_TIMESTAMP`）

#### M0-18 · 启动恢复（1d）
- 产出：`recover_on_boot()`：扫描 `running` 且 lease 过期的 turn → 从最后 `step` 续跑或标 `recovered`
- 验收：kill -9 后重启，turn 状态 `running→recovered`；事件 seq 连续；不重复执行已完成 step
- 风险：重复副作用 → M0 假 runner 无副作用；真实工具在切片① 加幂等键

#### M0-19 · `kill -9` e2e（0.5d）
- 产出：`tests/e2e/test_kill9.py`
- 做法：subprocess 启动 runner → 等第 2 条事件 → `kill -9` → 重启 → 断言恢复
- 验收：`make test-recovery` 通过；连续跑 10 次不 flaky
- 风险：Windows 无 SIGKILL → 用 `taskkill /F`，测试里按平台分支

### D 线 · 观测与交付

#### M0-20 · JSON 日志 + trace_id（0.5d）
- 产出：`platform/telemetry/log.py`：单行 JSON，字段 `ts/level/trace_id/tenant_id/event/...`
- 验收：一次假 turn 的所有日志共享同一 `trace_id`；无明文密钥
- 风险：日志噪音 → 只允许 INFO/WARN/ERROR，debug 走环境变量

#### M0-21 · 恢复演示脚本（0.5d）
- 产出：`scripts/demo_kill9.py` + `docs/demo/M0-recovery.md`（步骤与预期输出）
- 验收：一条命令跑完"启动→杀→恢复→打印事件链"，退出码 0
- 风险：演示依赖本机路径 → 全部用相对路径与临时目录

#### M0-22 · M0 验收报告模板（0.5d）
- 产出：`docs/reports/M0-acceptance.md` 模板：环境、迁移矩阵、恢复演示、指标、遗留
- 验收：填完后能直接用于 G-M0 评审
- 风险：模板变成形式 → 每项必须是命令输出粘贴

#### M0-23 · 快速开始（0.5d）
- 产出：`README` 新增"10 分钟跑通"：clone → `uv sync` → `poly doctor` → `poly migrate` → `make test`
- 验收：干净机器（或新目录 + 新 venv）照做一次成功
- 风险：隐式依赖本机工具 → 明确版本表与失败排查

### E 线 · 门禁与评审

# 14 · 竞品对标与组件选型

> 口径：基于公开仓库/文档与产品体验（2026-11），**许可证与功能以各项目当前版本为准**；本文只做架构与产品判断，不做功能评测。
> 目标：回答"市面上的开源 Agent 哪些值得学、我们的设计要改什么、哪些坑不能踩"。

---

## 1. 选谁做对标

按"是否覆盖 Agent 平台的完整链路"选 13 个，分四类：

| 类别 | 项目 | 为什么选它 |
|---|---|---|
| **Agent 平台** | OpenHands、Dify、Coze Studio、AutoGPT Platform | 覆盖"构建-运行-观测-扩展"全链路 |
| **编排/运行时** | LangGraph、CrewAI、AutoGen、Letta | 代表四种编排哲学（图/角色/对话/有状态） |
| **垂直 Agent** | SWE-agent、Goose、Cline | 工具界面、MCP、本地执行做得深 |
| **知识与前端** | RAGFlow、LobeChat / Open WebUI | RAG 管线与聊天 UX 的标杆 |

> 说明：Coze Studio 采用 Apache 2.0 并支持商用；Dify 的许可证带附加条件（多租户 SaaS/品牌），商用前必须核对；n8n 是 source-available（Sustainable Use License），不是 OSI 开源。其余以仓库 LICENSE 为准。

## 2. 全景：它们各自强在哪

| 项目 | 定位 | 真正的强项 | 明显的弱项 | 我们借鉴什么 |
|---|---|---|---|---|
| **OpenHands** | 软件工程 Agent 平台 | **事件流 + 沙箱 runtime + 可回放**；前后端一体 | 只面向编码；资源重 | 事件流设计、runtime 隔离、回放 |
| **Dify** | LLM 应用平台 | 可视化 workflow、RAG、**插件市场**、多模型 | Agent 运行时浅；DSL 锁定 | 插件市场形态、workflow 节点 UX |
| **Coze Studio** | Agent/Workflow 构建平台 | 产品化程度高；**插件 + 知识 + 发布**闭环 | 开源版与云版有差距；生态绑定 | 插件/发布/渠道的产品化路径 |
| **AutoGPT Platform** | 自动化 Agent 平台 | 前端 builder、block 生态、连续运行 | 抽象重、可靠性争议 | "连续运行"的产品表达 |
| **LangGraph** | 图编排库 | checkpoint、human-in-loop、子图 | 把运行时状态当业务真相 | 中断/恢复语义；**不学它的存储耦合** |
| **CrewAI** | 多 Agent 角色协作 | 上手快、角色/任务抽象直观 | 生产可观测性弱；角色扮演式协作易失控 | 任务分解的表达；**不学角色扮演** |
| **AutoGen** | 多 Agent 对话框架 | 对话式协作、研究生态 | 状态/部署弱 | 多 Agent 消息契约 |
| **Letta** | 有状态 Agent 运行时 | **memory blocks / 自我编辑记忆** | 是 runtime，不是库 | 记忆块的 user/agent 双区设计 |
| **SWE-agent** | 编码 Agent 研究 | **ACI（Agent-Computer Interface）**：命令/反馈/错误信息为模型而设计 | 研究原型 | 工具输出的"为模型设计" |
| **Goose** | 本地编码 Agent | MCP extensions、本地执行、桌面集成 | 通用工作流弱 | MCP 扩展模型、本地执行体验 |
| **Cline / Continue** | IDE 编码 Agent | 计划/审批/ diff 审阅的交互 | 非平台 | 审批与 diff 的微观交互 |
| **RAGFlow** | 文档 RAG | 深度解析（表格/扫描件）、切片可视化 | 编排弱 | 解析与切片调试面板 |
| **LobeChat / Open WebUI** | 聊天前端 | 多模型、插件、UX 细节 | 后端 Agent 能力弱 | 聊天页细节、模型切换 |

**一句话总结**：没有一家同时把"工作入口 + 授权 + 持久化执行 + 记忆 + 插件市场 + 优秀 UI"做全。**我们的机会正是这个组合**。

## 3. 组件维度对标

### 3.1 执行模型与恢复

| 做法 | 代表 | 评价 | 我们的选择 |
|---|---|---|---|
| 内存中的 agent loop，断线重连靠 session | 多数聊天型产品 | 简单，但重启丢活 | ❌ |
| 图编排 + checkpoint 恢复 | LangGraph / Dify workflow | 恢复好，但 checkpoint 与业务真相耦合 | ⚠️ 只借语义 |
| **事件流 + 沙箱 runtime + 可回放** | OpenHands | 最接近"生产级" | ✅ 我们的 `events + Turn/Run/Step` |
| 连续运行 + block 图 | AutoGPT Platform | 产品表达好，可靠性存疑 | ⚠️ 借"连续运行"概念 |

**结论**：我们的"事件溯源 + 租约 + 可恢复 turn"方向正确；需要补 OpenHands 式的**运行回放 UI**（`04` 已有轨迹，但缺"重播"）。

### 3.2 上下文管理

| 做法 | 代表 | 评价 |
|---|---|---|
| 固定截断 / 只保留最近 N 轮 | 多数早期产品 | 丢信息 |
| 服务端 compaction + tool-result clearing + memory tool | Anthropic 三件套 | **分层清晰，值得照搬模式** |
| 自动摘要 + 向量召回历史 | 部分平台 | 召回噪声大 |
| 子 Agent 隔离 | Claude Code / DSH | 最彻底 |

**我们的差距**：`13` 已补"压缩/清除/引用图/探针校验"，但**缺"压缩后探针自动化"与"子 Agent 上下文隔离"的产品化**。调整：M2 加"上下文调试面板"（每段 token、压缩前后、探针结果）。

### 3.3 记忆

| 做法 | 代表 | 评价 |
|---|---|---|
| memory blocks（user/agent 双区，模型可编辑） | Letta | 简单有效，适合"人格 + 偏好" |
| 抽取 → 去重 → 冲突 → 检索 | mem0 类 | 工程完整，但策略黑盒 |
| 时序知识图谱 | Zep/Graphiti | 适合"事实随时间变化" |
| 每日摘要 + MEMORY.md + atoms | Octop | 分层清楚，但耦合 harness |

**我们的选择**：`13` 的"端口 + 自研策略 + pgvector"，记忆块（USER/MEMORY）+ atoms 并存；图谱 v1.5。

**要补的**：Letta 式"模型自我编辑记忆"要加**审批**（写记忆是副作用），不能默认放开。

### 3.4 工具、MCP 与插件市场

| 做法 | 代表 | 评价 |
|---|---|---|
| MCP 作为唯一扩展协议 | Goose / Claude Code | 生态统一，但缺 UI 扩展 |
| 插件 = manifest + 后端代码 + 前端 UI | Octop / Coze | 体验完整，安全弱 |
| 插件市场 + 安装量 + 分成 | Dify / Coze | 商业闭环，但审核成本高 |
| Block/节点市场 | AutoGPT / n8n | 偏自动化，不是 Agent 能力 |

**我们的差距**：
1. 插件**权限声明 + 签名 + 沙箱**（`03` 已提，未细化）；
2. **市场**只有"从 Git/ZIP 安装"，缺评分、版本、兼容矩阵、下架；
3. 插件 UI 协议（`04` §7）需补**版本协商**与**降级渲染**。

### 3.5 多智能体编排

| 做法 | 代表 | 问题 |
|---|---|---|
| 角色扮演（Role/Goal/Backstory） | CrewAI | demo 好，生产难；角色不是权限边界 |
| 对话式群聊 | AutoGen | 收敛慢、成本高 |
| 图/状态机 | LangGraph | 可控，但学习曲线 |
| 协调者 + 成员（团队） | Octop / 我们 | 接近真实协作 |
| 工单 + 派工（Super-agent） | DSH | **最适合"工作系统"** |

**结论**：我们的 `Ticket/Assignment` 比"角色扮演"更接近生产；团队作为 Executor 内模式是对的。**不要引入"角色市场"**。

### 3.6 知识 / RAG

| 做法 | 代表 | 评价 |
|---|---|---|
| 固定切片 + 向量 | 多数 | 快，质量一般 |
| 深度解析 + 可视化切片 | RAGFlow | 解析强，部署重 |
| 图谱 RAG | GraphRAG / LightRAG | 全局问题强，索引贵 |
| 混合检索 + rerank + 引用 | 我们的 `03` §7 | 方向对，缺评测 |

**调整**：v0.5 先做"pgvector + 结构感知切片 + 引用"；RAGFlow 作为**可选外挂**（复杂文档），不做默认依赖。

### 3.7 UI / 可观测

| 做法 | 代表 | 借鉴 |
|---|---|---|
| 事件流时间轴 + 回放 | OpenHands | 运行详情/重播 |
| 节点级调试（输入/输出/耗时） | Dify / n8n | 工作流试运行 |
| 对话内 diff 审阅 | Cline | 代码变更审批 |
| 任务中心 + 注意力收件箱 | Super-agent | 我们的 `12` |
| 多模型/多 Provider 切换 | LobeChat | 模型选择器细节 |

**差距**：缺"工作流试运行（dry-run）"与"运行重播"；`12` 有任务中心但没有"从任务跳到 trace"的完整链路（`11` 有 trace_id，UI 未接）。

### 3.8 部署与许可

| 项目 | 部署形态 | 许可注意 |
|---|---|---|
| OpenHands | Docker / K8s | 以仓库为准 |
| Dify | Docker / K8s | **附加条件**，商用核对 |
| Coze Studio | Docker | Apache 2.0（可商用） |
| n8n | Docker / npm | **Sustainable Use**，非 OSI |
| LangGraph/CrewAI/AutoGen | 库 | 宽松 |
| RAGFlow | Docker | Apache 2.0 |

**启示**：自托管产品的许可证要"干净"（Apache/MIT），否则企业客户法务会卡。**我们坚持 Apache-2.0/MIT 依赖**，并在 `NOTICE` 里标注。

## 5. 五个"不要抄"

1. **不要把 LangGraph checkpoint 当业务真相**。Octop 已经用四套存储证明过代价。
2. **不要把可视化 DSL 当唯一编排**。Dify/Coze 的 DSL 好用，但一旦成为唯一入口，复杂逻辑就写不出来；我们的选择是"DSL 生成 Ticket/Workflow，底层仍可编程"。
3. **不要做"角色扮演式"多 Agent**。Role/Goal/Backstory 适合演示；生产要的是权限、工单、可审计。
4. **不要做"连接器即一切"**。n8n 的 400+ 集成很香，但 Agent 需要的是"工具语义 + 审批 + 结果渲染"，不是 HTTP 节点堆叠。
5. **不要过早做插件市场**。先用 Git/ZIP + 本地目录把 10 个高质量插件跑通，再谈市场与分成。

## 7. 结论

- **架构方向是对的**：事件溯源、Ticket/Assignment、Mandate、能力端口，比多数开源项目更接近"生产级工作系统"。
- **最该补的不是新概念，而是"可观测的闭环"**：回放、dry-run、trace 跳转、探针、评测——这些决定"能不能定位问题"。
- **最该克制的**：插件市场、图谱记忆、角色协作。它们看起来性感，但会在 v1 前吃掉大量工期且不解决稳定性。
- **许可证要干净**：依赖审计进 CI；商用前逐项核对 Dify/n8n 这类附加条件。

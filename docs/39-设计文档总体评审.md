# 39 · 设计文档总体评审与 Octop 差距

> 范围：`docs/01–38` 全量设计文档 + `contracts/` + `prototype/`。
> 问题：设计是否合理、是否完善；与 Octop 1.0.3b4 相比还差什么；哪些会影响后续功能与体验。
> 结论：**架构方向合理，规格覆盖广，但“文档治理、体验深度、范围控制、关键机制验证”四项不完善。**

---

## 0. 结论先行

| 判断 | 说明 |
|---|---|
| 合理 | 分层、事件溯源、Executor 端口、多租户、单一策略引擎、契约先行，方向正确 |
| 覆盖广 | 48 份文档 / 2 万行；157 条需求；188/242 个端点进契约；94/94 张首版表有 DDL；61 类事件 |
| 不完善 | 文档权威源不唯一、旧计数漂移；新域只有状态表没有交互原型；范围大于 4 人 28 周产能；关键机制未做技术验证 |
| 与 Octop 比 | PolyOpus 架构更正确；Octop 在**实现成熟度、交互细节、记忆引擎、技能披露、云主机/多实例**上仍领先 |
| 最大风险 | 不是“想漏了”，而是**设计面太宽、验证太少、文档本身开始漂移** |

一句话：**这是一份“可以开工但需要先收口”的设计，不是“已经完善”的设计。**

---

## 1. 文档体系健康度

| 指标 | 现状 | 评价 |
|---|---|---|
| 文档数 | 48 份 / 约 2 万行 | 覆盖广，但维护成本高 |
| 权威源 | `28–34` 是基线，`35–38` 是增量补丁 | 新读者难以判断“以哪份为准” |
| 历史文档 | `01–27` 含大量旧假设/旧计数 | 未标注“历史”，容易误用 |
| 跨文档一致 | 仍有漂移：README 写“82 条需求”、`35` 仍写 b2、`28` 引用 `31 §3.8` | 影响可信度 |
| 需求→契约 | 188/242 端点，54 个 backlog 已明列 | 比“假装 100%”好，但仍未闭环 |
| 需求→测试 | 157 个测试 ID，0 个用例 | 覆盖门禁只能 WARN |
| 交互原型 | 8+3 外壳 + 旧页面；云主机/通知/团队/三 Tab 工作台未进原型 | 设计与可点击体验脱节 |

**结论**：文档“多”不等于“健康”。当前最需要的是**权威源收敛 + 旧文档归档 + 计数自动校验**，而不是继续加文档。

---

## 2. 设计合理的地方

1. **执行模型**：Turn/Run/Step 持久化 + 租约，解决 Octop “状态在进程内”的根本问题。
2. **事件溯源**：`events` 单一真相 + `messages` 投影，避免 Octop 四套会话存储并存。
3. **模块边界**：`kernel/platform/domains/api/workers` 分层 + 依赖方向 CI，避免上帝对象。
4. **治理收敛**：单一策略引擎 + `allow/ask/deny + obligations`，比 Octop 五套并行正确。
5. **多租户**：全表 `tenant_id` + repo 强制过滤，企业化入场券。
6. **契约先行**：OpenAPI/事件/生成类型 + `coverage_check.py`，比 Octop 手写类型可维护。
7. **懒 Ticket**：只读对话不建 Ticket，写/审批/预算/异步才升级，兼顾体验与治理。
8. **ACL 两层**：RBAC 能力 + 可见性 grant，默认私有，避免 Octop 的 fail-open。

## 3. 主要不足（按优先级）

### P0 · 会直接影响后续功能/返工

| ID | 不足 | 证据 | 影响 |
|---|---|---|---|
| A-01 | **文档权威源不唯一** | `28–34` 基线 + `35–38` 补丁 + `01–27` 历史 | 实现者按旧文档写，必然返工 |
| A-02 | **范围大于产能** | 87 表 / 214 端点 / 61 事件 / 8+3 页面；4 人 28 周 | 每块都做一点，核心闭环不深 |
| A-03 | **新域只有状态表，没有交互原型** | 云主机、通知、团队、三 Tab 工作台只在 `30/04` 文本里 | 前端实现靠猜，体验与 Octop 差距扩大 |
| A-04 | **关键机制未验证** | 事件重放/投影重建、租户隔离、插件沙箱、策略引擎、记忆质量均无 spike | M1 后才发现不可行，返工成本最高 |
| A-05 | **测试闭环为空** | 157 个测试 ID，0 用例；`coverage_check` WARN 157 | 无法证明 “MUST 真的可用” |
| A-06 | **旧计数/旧引用漂移** | README 写 82 条需求；`35` 仍写 b2；`28` 引用 `31 §3.8` | 评审/新人判断失真 |

### P1 · 影响体验与可运营性

| ID | 不足 | 说明 |
|---|---|---|
| B-01 | **交互细节落后 Octop** | 技能渐进披露、系统通知、云主机授权、隐藏专家、技能包文件树、token 缩写、头像选择，Octop 已有实现，PolyOpus 只有部分规格 |
| B-02 | **错误文案/空态/加载态不完整** | `30` 覆盖主流程，但新域（云/通知/团队）缺空态、错误码文案、重试策略 |
| B-03 | **移动端/PWA 只有原则** | `04 §9` 有响应式原则，无页面级验收；Octop 有 PWA 与移动布局 |
| B-04 | **可访问性/i18n 未落验收** | `04 §10` 有原则；`30 §15` 仍有未勾选项 |
| B-05 | **性能/容量未验证** | `02` NFR、`17` 容量模型是估算；无压测脚本/结果 |
| B-06 | **多实例 T2 只有架构图** | `17` 有 API×2–4 + Redis + scheduler leader，但无实例注册/缓存失效/配置共享表 |

| B-09 | **迁移/回滚未演练** | `18` 有映射；无双跑/差异报告/回滚窗口 |
| B-10 | **插件沙箱只有原则** | `02 §8.3` 写了子进程；无权限清单、网络代理、资源限额细节 |

## 4. 与 Octop 的差距

### 4.1 Octop 仍然更强的地方

| 维度 | Octop b4 | PolyOpus | 差距性质 |
|---|---|---|---|
| 实现成熟度 | 534 handlers / 551+ 测试 / 真实用户 | 0 实现 | 阶段差距 |
| 记忆引擎 | raw→candidate→atom→episode→entity/page；BM25+rerank；200ms | 逻辑三层；无 episode/entity；无 BM25 参数 | 深度差距 |
| 技能机制 | 渐进披露 + per-turn allowlist + 文件树 + 共享 | 规格已写，无原型/实现 | 落地差距 |
| 云主机 | 授权/实例/指标/启停/AI 运维，已上线 | v1.1 文档，无原型 | 体验差距 |
| 多实例 | PG 共享 cron/channel/avatar/plugin/published expert | T2 架构图，无共享表/失效机制 | 机制差距 |
| 通知 | 后台标签页系统通知 | 文档已补，无原型 | 体验差距 |
| 交互细节 | 隐藏专家、token 缩写、头像、技能包文件树 | 部分只有规格 | 细节差距 |
| 渠道/设备 | 飞书/钉钉/企微/QQ/桌面/远程 | 首版 3 渠道；桌面/远程延后 | 范围差距 |

### 4.2 PolyOpus 更强的地方

| 维度 | 说明 |
|---|---|
| 持久化执行 | Turn/Run/Step + 租约，重启可恢复；Octop 团队任务/浏览器会话进程内 |
| 事件溯源 | 单一真相 + 投影；Octop 四套存储 |
| 多租户 | 全表 `tenant_id` + repo 过滤；Octop 无租户 |
| 工具治理 | 单一策略引擎 + 执行期校验；Octop 五套并行、prompt 过滤 |
| 插件安全 | api_version + permissions + 签名 + 子进程；Octop 任意 Python |
| 知识检索 | 结构切片 + hybrid + rerank + 引用 span + 评测；Octop 固定 800/120 + 暴力 cosine |
| 契约 | 158 操作 / 61 事件 / 生成类型 + 覆盖门禁；Octop 手写类型 |
| 审计 | 工具调用/审批/记忆变更；Octop 只覆盖管理动作 |

**结论**：Octop 赢在“已经跑起来 + 交互打磨”；PolyOpus 赢在“架构正确 + 可演进”。不要用“功能数量”去追 Octop，应该用“核心闭环质量”去赢。

## 5. 对未来功能/体验的具体影响

| 功能域 | 设计风险 | 未来影响 |
|---|---|---|
| 对话 | 懒 Ticket 已定稿，但前端还没有“升级为任务”的交互 | 用户不知道什么时候对话变成任务；审批/预算出现时缺少解释 |
| 任务中心 | 87 张表/多状态机已定，但无端到端验收 | 状态展示与真实执行不一致，排障困难 |
| 专家/技能 | 渐进披露规格有了，原型没有 | 技能多时上下文仍可能爆；用户不知道技能何时生效 |
| 知识库 | hybrid/rerank 规格完整，但无评测集与 SQLite 降级实机 | 质量不达标时无法定位是切片、embedding 还是 rerank |
| 记忆 | 三层逻辑，缺 episode/entity；无抽取幂等 | 长会话记忆质量低于 Octop；重启可能重复抽取 |
| 团队/派工 | 表/API/事件齐，但交互只有状态表 | 成员忙/失败/重派的可视化不足，用户不信任 |
| 渠道 | 3 渠道 + 绑定/消息规格，但无真实平台联调 | 入站幂等/身份归属容易出错 |
| 控制面 | 终端/浏览器/云主机有规格，原型只有 2 Tab | 新 Tab 的权限、空态、危险确认没有可点击验证 |
| 管理端 | 用户/角色/分组/配额/审计齐，但无批量/导入细节 | 企业部署时运维成本高 |
| 通知 | 表/API/事件/UI 齐，但无系统通知权限/降级原型 | 后台任务完成不可见，用户以为没跑 |

## 6. 建议

### 6.1 文档治理（本周）

1. **确定唯一权威源**：`28–34` 为基线，`35–39` 为增量；`01–27` 顶部加“历史，不作为实现依据”。
2. **自动校验计数**：把 `28/29/31/11` 的计数做成 `coverage_check` 的一部分，防止 README/35 再漂移。
3. **修掉已知漂移**：README “82 条需求”、`35` 的 b2 基线、`28` 的 `31 §3.8` 引用。

### 6.2 范围收敛（本月）

建议 v1.0 只保留：

- 对话 + Turn/Run/Step + 审批
- 任务中心 + Intake（Web/Webhook）
- 专家 + 技能（渐进披露）
- 知识库（SQLite 单机路径）
- 记忆（三层 + 候选层）
- 用户/角色/分组/ACL
- 通知（站内）
- 用量/审计

**延后到 v1.1/v1.2**：团队/派工、渠道、控制面、云主机、工作流、Bridge、市场、桌面/移动。
理由：这些域每块都要 2–4 周，4 人团队同时做会让核心闭环不深。

### 6.3 技术验证（M0 前 2 周）

做 5 个 spike，每个 1–3 天，产出“可行/不可行 + 替代方案”：

1. 事件重放 + `messages` 投影重建（10k 事件）。
2. 租户隔离负向测试（跨租户 404/403）。
3. 策略引擎 + 工具执行期校验（fail-closed）。
4. 插件子进程 + 只读挂载 + 网络代理。
5. 记忆 20 条探针集（写入/召回/冲突）。

### 6.4 体验验收（M1 前）

1. 给云主机/通知/团队/三 Tab 工作台各做 1 个可点击原型（不必接后端）。
2. 每页补：空态、错误态、加载态、权限禁用、危险确认、快捷键。
3. 定义 5 个体验指标：首次可用时间、任务完成率、审批等待、错误恢复率、移动端可用。

### 6.5 质量门禁

- `coverage_check` 进 CI：HARD 阻断，WARN 跟踪。
- M1 起把 G-4（测试）从 WARN 升为阻断。
- 每个 MUST 至少 1 正 1 负用例；安全用例从 `20` 抽 10 条进 CI。

## 7. 评审结论

**合理**：架构、边界、治理、契约、多租户方向都对。
**完善度**：规格层约 80%，体验层约 55%，验证层约 10%，实现层 0%。
**与 Octop**：功能面已接近，体验细节和实现成熟度仍有明显差距；但 Octop 的结构性问题（无租户、五套治理、任意插件、双管线）不该追。
**最该做的三件事**：收敛权威源、砍 v1 范围、做 5 个技术 spike。  
**最不该做的**：继续加文档、继续扩功能面、在没验证前写大量代码。

## 1. P0（不补就返工）

### D-01 · ✅ 已定稿：统一执行基底 + 懒 Ticket

> 2026-11 已按 `ADR-012` 收口：所有入口走 `thread + turn`；只读对话不建 Ticket；写工具/审批/预算/异步时懒创建并回填 `turn.ticket_id`。
> 依据：`02 §3.6.1`、`32 §6`、`28 CHAT-015`。

**原问题**

- `02 §3.6` 写的是统一入口：`Source → Trigger → Eval → Ticket → Assignment → Executor`，并明确 **Turn 降级为 Executor 的内部实现**。
- 但 `32 §4` 的 `ConversationPort` 直接暴露 `append_user_message() -> Turn`；`ExecutionContext.ticket_id` 是 **可选**（`32 §6`）。
- `28 CHAT-001..014` 全部按“直接发 Turn”验收；M1 1.5 也是“对话 WS + Chat 页”，不经过 Ticket。
- 全仓没有“Web 对话是否创建隐式 Ticket”的规则。

**风险**

这会复刻 Octop 最严重的问题：**两套对话管线漂移**（一套走 checkpoint/WS，一套走 ticket/assignment），后面会出现“同样的消息，一边有审批/预算/审计，一边没有”。

**修复**

二选一并写进 `02 §3.6` / `32 §4`：

- **方案 A（推荐）**：每次 Web 对话创建一个**隐式 Ticket**（`strength=explicit`、`source=web`、`mandate` 来自会话策略），Turn 只是它的执行载体。好处：审批、预算、审计、恢复走同一条路。
- **方案 B**：明确“直接对话是受限执行”，不建 Ticket，但必须回答：谁授权工具、预算记在哪、崩溃怎么恢复、审计怎么串。代价是两套语义永久并存。

**验收**：同一句“读文件并改一行”在 Web 与 IM 两个入口，产生相同的 Mandate、预算、审批与审计记录。

### D-02 · ✅ 已定稿：资源 ACL 两层模型

> 2026-11 已按 `ADR-013` 收口：`02 §8.2` 定优先级；`31 §3.10` 加 `resource_group_grants`；`29 §3.15` 加 3 个端点；`28 ADM-014` 禁止 fail-open。
> 默认 private，无 grant 不等于公开。

**原问题**

- `02 §8.2` 声明了 `owner / team / tenant / public` 的资源 ACL。
- `31` 只有 `groups`、`group_members`、`knowledge_acl`，以及 `agents.visibility`；**没有 `resource_group_grants`**。
- `28 ADM-011` 只写“资源可见性可按组生效”，没有资源类型、授权对象、优先级规则。
- 租户/团队/分组/owner 四者冲突时谁优先，未定义。

**风险**

无法实现“技能包/KB/连接器/模型/存储/专家按组可见”；一旦实现，容易出现“无 grant = 公开”的 fail-open（Octop 的坑）。

**修复**

补一张通用表与规则：

```sql
resource_group_grants(
  tenant_id, resource_type, resource_key, group_id,
  permission, created_by, created_at,
  UNIQUE(resource_type, resource_key, group_id, permission)
)
```

规则写死：`tenant 边界 > owner > 显式 deny > group grant > 默认私有`；无 grant 默认**不可见**，不是公开。

**验收**：6 类资源 × 3 种角色（owner/组成员/无关用户）的可见性矩阵测试。

### D-03 · ✅ 已补齐：首版 87 张表全部有 DDL

> 2026-11：`31 §3.12` 一次补齐剩余 29 张首版表；现 95 张表 / 87 条 DDL，8 张候选表（workflows/workflow_runs/bridge/acp/thread_participants/source_cursors/agent_storage_bindings/feature_flags）明确延后。

repo/service 无法开工；实现者会各自补列，最终 schema 漂移。

**修复**

按垂直切片补：M1 先补 `user_mfa/api_keys/roles/groups/artifacts/tool_calls`；M2 补 `plugins/skill_packages/knowledge_acl`；M3 补渠道/团队/控制。每张表必须有列、索引、枚举、迁移与回滚。

### D-04 · ✅ 已定稿：通知领域模型

> 2026-11：`31 §2.10/§3.11` 加 `notifications`；`29 §3.16` 加 3 个端点；`11` 加 `notification.created`；`28 NOTIF-001..004`；`30 §14A.8` 加通知中心/系统通知状态。

**原问题**

- `11` 有 `attention.requested/resolved`（审批/提问/受阻），但没有“定时任务完成/失败”“云操作完成”“导出完成”这类轻量通知。
- `31` 没有 `notifications` 表；`29` 没有通知端点；`30` 没有通知中心/系统通知状态。
- Octop b4 已把后台标签页提醒改为系统通知，PolyOpus 没有对应设计。

**风险**

所有异步结果只能塞进 Attention，导致“待决事项”被噪声淹没；或者前端各自轮询，体验不一致。

**修复**

- 表：`notifications(id, tenant_id, user_id, kind, title, body, link, read_at, dedupe_key, created_at)`。
- 事件：`notification.created`（sys）。
- API：`GET /notifications`、`POST /notifications/{id}/read`、`POST /notifications/read-all`。
- 交付：站内 + Web Push（需权限，失败降级站内）；与 Attention 分开：Attention 需要人决策，Notification 只是告知。

### D-05 · ✅ 已定稿：新域错误码 / 状态机 / 事件闭环

> 2026-11：`29 §2.10–2.12` 补记忆/通知、渠道/控制、团队/云错误码；`32 §13A` 补 9 个状态机；`11` 补 5 类事件（61 类）。

**原问题**

- `29 §2` 错误码只到“用量/管理/运维”，**没有 CLOUD_/MEMORY_/CHANNEL_/NOTIFICATION_**。
- `32` 状态机只覆盖 Turn/Run/Assignment/OAuth/Doc，**没有 ControlSession、Cron、CloudOp、Delegation、MemoryAtom、Plugin**。
- `11` 事件缺 `control.*`、`workspace.file.changed`、`subscription.created`、`notification.created`。
- 契约声称 152 个操作、190 个 schema，但错误码与状态机没跟上。

**风险**

实现时每个域自己发明错误码和状态，前端无法统一处理，重试/补偿语义不一致。

**修复**

- 每个新域至少 3 个错误码：`*_NOT_FOUND`、`*_CONFLICT`、`*_UPSTREAM_FAILED`。
- 每个新域一张状态迁移表，非法迁移必须 409。
- 事件与状态机对齐：状态变更必须有事件，事件必须有消费者与保留策略。

### D-06 · ✅ 已实现：`contracts/coverage_check.py`

> 2026-11：脚本已落地。当前 `HARD: 0`；`WARN: 145`（测试用例尚未写，M1 前可接受）。`--strict` 可把允许清单也视为失败。

**原问题**

- `28` 有 145 条需求、每条有测试 ID，但仓库里没有测试。
- `contracts/check.py` 只校验事件/OpenAPI 生成一致，不校验“每个 MUST 是否有端点/表/测试”。
- `35` 的覆盖统计靠人肉维护。

**风险**

需求、契约、实现三张皮；新增端点不改 spec、新增 MUST 不写测试，CI 不会失败。

**门禁规格（实现时照此写 `contracts/coverage_check.py`）**

| # | 检查 | 失败条件 | 输出 |
|---|---|---|---|
| G-1 | 需求完整性 | `28` 中每个 MUST 无 `API/事件` 列 | `MUST_WITHOUT_CONTRACT: <ID>` |
| G-2 | 端点闭环 | `29` 端点不在 OpenAPI，或 OpenAPI 有 `29` 未列端点 | `ENDPOINT_MISMATCH: <method> <path>` |
| G-3 | 表闭环 | 需求引用的表不在 `31` 表清单 | `TABLE_MISSING: <ID> -> <table>` |
| G-4 | 测试闭环 | 需求有测试 ID，但 `tests/` 无同名用例 | `TEST_MISSING: <ID>` |
| G-5 | 事件闭环 | `32 §13A` 的状态迁移无对应事件 | `EVENT_MISSING: <object>.<transition>` |
| G-6 | 枚举闭环 | 新增错误码不在 `29 §2` | `ERROR_CODE_MISSING: <CODE>` |

**规则**

1. G-1/G-2/G-3 为硬门禁，失败即阻断合并。
2. G-4 在 M1 前只警告，M1 后升为阻断。
3. G-5/G-6 允许白名单，但白名单必须写理由与到期版本。
4. 输出为机器可读 JSON + 人读摘要，CI 直接贴 PR 评论。

## 2. P1（GA 前必须补）

### D-07 · 多实例 T2 只有架构图，没有共享机制

**现状**

- `17 T2` 画了 `api ×2–4 + worker ×4–8 + scheduler ×1 + Redis`，但没有：
  - `instances` 注册/心跳表；
  - 配置/权限/插件变更的跨实例失效；
  - cron 单飞与错过补跑的租约；
  - 云凭证/全局配置放控制面的表与 API。
- `31` 没有 `instances` 表。

**修复**：要么把 T2 降级为“单 API + 多 Worker”（v1 推荐），要么补 `instances`、`config_versions`、`cache_invalidation` 与 scheduler leader 规则。

### D-08 · 上下文预算固定 128k，没有按模型分档

**现状**：`13 §3.2` 的预算表是 128k 固定值；`13 §9` 只有 p95 目标，没有 token 计量校准。

**风险**：32k/200k 模型直接超限或浪费；压缩阈值在不同模型上行为不一致。

**修复**：定义 `ModelCaps.max_input_tokens` 三档（32k/128k/200k），预算表按比例缩放；用 provider usage 校准估算，不用字符数拍脑袋。

### D-09 · 记忆抽取缺幂等与候选生命周期

**现状**：`13 §4.1` 写了 raw→candidate→atom，但没有：抽取任务 lease/checkpoint、按 `event_id` 去重、失败重试上限、候选过期/清理、评测数据集。Octop b3 已专门修“重启后不重跑”。

**修复**：抽取任务加 `lease_until/attempts`；`memory_events(event_id)` 唯一；候选 TTL 30 天；补 20 条记忆探针集。

### D-10 · 成本只有账本，没有价格表与执行点

**现状**：`31 usage_ledger` 有 `cost_micros/price_version`，但没有 `model_prices` 表；`28 USE-001/002` 只做展示；预算执行点散落在 `budget_json`。

**修复**：补 `model_prices(model, currency, input_per_1k, output_per_1k, version, effective_at)`；在 ModelGateway、ToolRuntime、Embedding 三个入口统一扣减；超限返回 `QUOTA_EXCEEDED`。

### D-11 · 安全控制没有形成闭环

**现状**：`20` 有 70 条红队用例，`02 §8.3` 有沙箱，但缺：
- prompt injection 的入口/工具输出/记忆三层防线；
- SSRF 的统一出口代理；
- 密钥轮换与泄露检测；
- 租户隔离的自动化负向测试。

**修复**：把 `20` 的用例映射到 CI；新增“工具输出永不直接进 system prompt”“外链只走 egress proxy”“secret 版本与轮换”三条硬约束。

### D-12 · Agent 版本锁定与运行中会话迁移语义

**现状**：`28 EXP-007` 说“旧会话锁定旧版本”，`31 agent_versions` 有不可变快照，但没说：会话如何记住版本、发布后旧会话是否可切、运行中 Turn 用哪个版本、回滚对新/旧会话分别什么行为。

**修复**：`threads.agent_version_id` 固定；Turn 开始时快照 `agent_version_id`；发布/回滚只影响新 Turn；提供“升级会话到新版本”的显式操作。

### D-13 · ✅ 已定稿：数据导出/删除

> 2026-11：`28 ADM-015/016`、`31 data_jobs`、`29 /me/export` + `/admin/tenants/{id}`、`31 §3.11` 删除顺序已补。

**原问题**：`31 §6` 有保留策略；`01 K10` 提了 GDPR 类导出/删除，但 `28/29` 没有对应需求与端点；事件、artifacts、向量、记忆、审计的删除顺序未定义。

**修复**：补 `POST /me/export`、`DELETE /admin/tenants/{id}`；定义删除顺序：业务行 → 向量 → 对象存储 → 事件归档 → 审计保留；审计只匿名化不删除。

### D-14 · Executor 契约的 ticket_id 可空，外部执行器语义不完整

**现状**：`32 §6` 的 `ExecutionContext.ticket_id` 可选；外部 executor 只有 `execute/cancel/capabilities`，没有流式事件、心跳、report 幂等、恢复点。

**修复**：与 D-01 一起收口：要么 ticket_id 必填，要么明确“直接执行”模式；补 `ExecutorEvent`（delta/progress/report/heartbeat）与 `resume(run_id)`。

### D-15 · 知识检索的 ACL 顺序与降级路径未写死

**现状**：`03 §7` 写了 hybrid + RRF + rerank，但没写：ACL 过滤在 embedding 前还是后、SQLite 单机如何降级、rerank 不可用时是否回退、引用 span 的存储格式。

**修复**：ACL 先过滤 KB 再 embedding；SQLite 用 FTS5 + sqlite-vec；rerank 超时回退 RRF；`chunks` 存 `page/char_start/char_end`。

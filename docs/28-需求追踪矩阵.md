# 28 · 需求追踪矩阵

> 目的：把"功能清单"变成可验收、可追踪、可排期的需求集合。
> 每条需求必须有：唯一 ID、验收句、页面入口、API/事件、数据表、测试、当前状态。
> 参考 Octop 的做法：路由/权限/迁移/错误码都有稳定标识；区别是我们先冻结需求 ID 和垂直切片，再写实现。

---

## 0. 使用方式

### 0.1 状态图例

| 标记 | 含义 |
|---|---|
| `D` | 设计完成（文档/交互/接口足够开发） |
| `P` | 原型可演示（`prototype/` 可点通） |
| `B` | 后端已实现（当前为 0） |
| `T` | 自动化测试已覆盖（当前仅原型 CDP） |

### 0.2 优先级

| 级别 | 含义 |
|---|---|
| `MUST` | v1.0 必须；缺失不能发布 |
| `SHOULD` | v1.1 应做；可在灰度后补 |
| `COULD` | 体验增强；不阻塞 |
| `LATER` | 明确不在 v1 |

### 0.3 需求 ID 规则

```
域-序号
AUTH / TEN / CHAT / TURN / TASK / INTAKE / EXP / CONN / EXT / KB / USE / ADM / UX / OPS
```

### 0.4 验收句规则

每条需求必须写成：

> **当**（前置条件）**，用户/系统**（动作）**，**（可观察结果）**，且**（失败/边界）**。

例：

> 当用户发送空消息时，发送按钮禁用；强行 Enter 不产生 Turn，输入不丢失。

## 1. 范围冻结（v1.0）

### 1.1 必做

- 单租户可用、可扩展到多租户
- 对话 + Turn/Run/Step 持久化
- 任务中心 + Intake（Web/Webhook）
- 专家、连接器、知识库、扩展
- 8+3 导航、权限、错误模型
- 用量、管理端、审计
- 通知、备份/恢复、迁移、基础可观测

### 1.2 明确不做

| 项 | 原因 | 去向 |
|---|---|---|
| Ticket 拆分 | 先合并，避免双对象 | v1.2 |
| 多租户计费 | 先单租户配额 | v1.3 |
| 插件市场签名 | 先本地签名白名单 | v1.2 |
| 移动端原生 App | 先 PWA/响应式 | v2 |
| 多活部署 | 先单实例 + 只读副本 | v2 |
| 工作流 DAG | 节点级重试/补偿复杂度高 | v1.5（表先建不启用） |
| 会话级 fork | v1 只做 Turn 级分支 | v2 |
| OCR | 先依赖 PDF 文本层，扫描件明示 | v2 |
| 语音 STT/TTS | 接口预留，先接浏览器 Web Speech | v2 |
| 远程桌面 / 移动控制 | 安全面过大 | v2 / 不做 |
| 团队/派工 | 依赖 Ticket/ACL 稳定后再做 | v1.1 |
| 渠道（IM） | 先 Web/Webhook 入口 | v1.1 |
| 来源覆盖 | v1 只启用 Web / webhook / schedule；GitHub、邮件、IM 全部 v1.1 | v1.1 |
| 控制面（终端/浏览器） | 安全与审计面大 | v1.1 |
| 云主机（CVM） | 独立域，先设计后实现 | v1.1 |

## 5. 追踪维护规则

1. 新增页面/按钮必须先有需求 ID，否则不进入开发。
2. PR 描述必须引用需求 ID；CI 检查 `docs/28` 是否存在该 ID。
